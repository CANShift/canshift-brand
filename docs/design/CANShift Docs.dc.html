The packages

Four repositories under the CANShift org — core ships to npm.
canshift-firmware
C++17 · LVGL 8.4 · own repo

Parses CAN over TWAI, decodes signals, drives the panel. Source of truth for the runtime.

canshift-core
TypeScript · Zod · npm 0.9.4

Shared domain — schemas, signal map, design tokens. Published to npm as @canshift/core, consumed by tuner and mobile.

canshift-tuner
Vite + React · own repo

SPA on Vercel, talks to the dash over Web Serial. Editing, CAN scan, firmware flash.

canshift-mobile
Expo · iOS + Android · own repo

Pairs over BLE for in-car telemetry and secondary config. One codebase, shipped on iOS and Android.

FW ≥ 1.6.0 WIRE v2 UPD 23.07.2026

Cruise is a page widget like any other: it reads two CAN signals (VEHICLE_SPEED and CRUISE_STATE) and renders a polygon whose vertices are recomputed on every tick.

DANGER
Cruise does not brake. On track, cut it at the box: the firmware cannot guarantee resume if the bus drops below 5 frames/s.

Arming from the dash

  1. Go to the page carrying the Cruise widget (swipe or page button).
  2. Hold the centre zone for 400 ms — the ring goes armed.
  3. Target speed locks to the current value, rounded to the km/h.
NOTE
On ECU profiles without CRUISE_STATE, the widget falls back to a value derived from RPM + gear. Accuracy ±2 km/h.

The payload sent

src/widgets/cruise_widget.cpp C++ 
// armed → the target is frozen, the polygon redraws
void CruiseWidget::arm(uint16_t kph) {
  state_ = CruiseState::Armed;
  target_ = kph;
  lv_obj_invalidate(ring_);   // no lv_obj_clean here (#1102)
}
TIP
The Tuner exposes the same state live in the Live data tab — handy for validating an ECU profile without driving.

Cut and resume

Any brake press visible on the bus cuts the state within a tick. Resume reuses the last target as long as the page has not been rebuilt; changing page clears the widget and the target with it.

CAUTION
Do not fit the 120 Ω terminators unless the dash sits at a physical end of the bus. Most cars are already terminated at both ends — a third resistor drops the bus to ~40 Ω and the ECU stops talking.

Substitutions that work

Any ESP32 + ILI9341 panel
Keep the GPIO contract from Pinout and the firmware builds unchanged. WROVER boards work too — the PSRAM is simply unused.
SN65HVD230 instead of TJA1051
Cheaper and widely cloned. Slew-rate pin must be grounded; expect more errors above 500 kbit/s.
Buying from a Western distributor
Mouser and DigiKey stock equivalent ESP32 panels for around $48 — fifteen dollars more, two weeks less.

TECHNICAL/ARCHITECTURE/BOOT SEQUENCE

Boot sequence

The heap reservation order that makes boot fit on a no-PSRAM WROOM. Re-ordering the early stages bricks the device.

CRITICAL src/boot/boot_sequence.cpp

The contiguous-block budget

On the production board, the largest free DRAM block after Arduino init is ~120 KB. Several consumers each need a large contiguous chunk.

CONSUMERRESERVATIONNOTES
NimBLE early init~50 KBfails ~16 KB after lv_init
LVGL pool~80 KBonce claimed, fragments the remainder
USB rxBuf~16 KBdoubles as the PUT_CONFIG buffer
TWAI init stack~4 KBpre-reserved in CanManager
ArduinoJson parse~20 KBduring ConfigLoader::loadAll

Required ordering

setup() — main.cpp → boot_sequence.cpp CALL TREE 
setup()
  ├─ Serial.begin                        UART up so logs land
  ├─ UsbComm::reserveRxBuf()             ~16 KB BEFORE lv_init
  ├─ CanManager::reserveInitTaskStack()  ~4 KB BEFORE lv_init
  └─ BootSequence::run()
       ├─ silenceNvsLogNoise             nvs ERR → WARN
       ├─ initPsramAndLogEntry
       ├─ initTaskWatchdog
       ├─ initBleEarlyIfEnabled            NimBLE ~50 KB
       ├─ mountStorageOrLogError         SPIFFS
       ├─ provisionDefaultConfigsIfNeeded
       ├─ loadConfigWithHeapBracket      ArduinoJson ~20 KB
       ├─ initDisplayAndLVGL               lv_init claims ~80 KB
       ├─ initTouchHardware
       ├─ initLvglFsIfStorageOk
       ├─ provisionDefaultFontsIfNeeded
       ├─ initFontManagerWithHeapLog
       ├─ preloadIconsWithHeapLog        SPIFFS while the heap is large
       ├─ showSplashWithInitialUpdates
       ├─ initRuntimeServices
       ├─ initCanHardwarePhase
       ├─ initUsbCommPhase
       ├─ buildUiWithHeapBracket         PageManager::init
       ├─ holdSplashUntilMin (2000 ms)
       └─ logBootCompleteAndReady        "[BOOT] Ready"
DANGER
After lv_init, the largest contiguous block drops to ~13–18 KB. Anything larger must have been reserved before. PR #1374 / #1376.

Why each ordering matters

reserveRxBuf before lv_init
USB_RX_BUF_SIZE ≈ 16 KB and the TWAI stack ~4 KB — both right at the cliff once LVGL has claimed its pool.
initBleEarlyIfEnabled before the display
After LovyanGFX init the largest free block drops to ~16 KB, making BLE impossible. earlyInit reserves the arena while the heap is still clean.
lv_init before DisplayDriver::init
s_lcd.init() fragments the heap such that the LVGL pool malloc no longer fits. LVGL first, display registration after.
updateSplash("Ready") before buildUI
PageManager::init calls lv_obj_clean(lv_scr_act()) and frees the splash objects. Any updateSplash after that point derefs freed memory.
NOTE — CI
The smoke test firmware-boot-smoke.yml asserts that [BOOT] Ready appears exactly once. Do not move or reword the line.
